# 2026-11-17 工作日志（rk3588_handover / railhmi）

## 本轮需求（门磁延迟收尾）
用户问「为什么门磁反应还是这么慢，是否可以在 5s 以内识别新状态」。之前 round-5 尝试「BlueZ discovery + 周期裸 HCI 关去重」在板端失败——裸 HCI 命令与 BlueZ discovery 互斥，导致 `Discovering=false / Device1 count=0`。

## 关键根因与实现
- **裸 HCI 与 BlueZ discovery 互斥**：bluetoothd 在 discovery 期间约每 10s 重新下发 `LE Set Scan Enable` 并重新打开 `Filter duplicates`；第三方下发裸 HCI 命令后，BlueZ 会卡在 `InProgress / Discovering=False / Device1=0`。
- **生产主路径改为 HCI 原始直读**：`DoorSensorWorker` 在独立 `QThread("railhmi-door-io")` 中：
  - `openBleAdvSocket()` 打开 `HCI_CHANNEL_RAW` 非阻塞套接字；
  - 下发 `LE Set Scan Parameters` + `LE Set Scan Enable(filter_dup=0)`；
  - `QSocketNotifier` 事件驱动读取 `EVT_LE_META_EVENT / LE Advertising Report`；
  - 直接解析 `AD type 0xFF` 中 `company=0xFF07` 的 23B 厂商字段，构造 `pushedFrame` 给 GUI；
  - `refreshRawScan()` 每 2s 重发 `filter_dup=0`，覆盖 bluetoothd 的 10s 周期；
  - 退出时 `disableBleScan()` 关闭扫描。
- **BlueZ 降级路径**：无 `CAP_NET_ADMIN+CAP_NET_RAW` 时回到私有 system-bus + `SetDiscoveryFilter(Transport=le,DuplicateData=true)` + `StartDiscovery` + 1s `GetManagedObjects` + 正确接口 `org.freedesktop.DBus.Properties` 的 `PropertiesChanged`。
- **权限**：`packaging/railhmi.service` 已加 `ExecStartPre=-+/usr/sbin/setcap cap_net_admin,cap_net_raw+ep /opt/railhmi/bin/railhmi`。
- **配置**：`app/config/app.yaml` `poll_interval_ms: 1000`（范围仍 1000..10000），`stale_ms: 60000`。
- **解析器**：保留 PDF 的 Key `0x08`，同时以 `vendor_tolerant` 识别现场固件真实的 Key `0x06`（后 1B 布尔，0=closed/1=ajar）。
